STRIDE na prática: controles no código

O modelo de ameaças só reduz risco quando se torna comportamento verificável no servidor: identidade confiável, dados controlados, auditoria, autorização e limites de uso.

Pergunta-guiaQual decisão de código impede cada ameaça STRIDE no sistema de matrículas?

Construa o conceito

STRIDE no código

SSpoofing: a sessão define a identidade⌄

Não aceite o identificador do estudante como prova de quem faz a solicitação. Valide a sessão, obtenha a identidade autenticada e verifique a permissão.

TTampering: o cliente envia intenção⌄

Aceite apenas campos necessários, como a turma. Prioridade, status, identidade e regras devem ser buscados ou calculados no servidor.

Resultado: evita que o cliente defina campos internos por atribuição em massa.

RRepudiation: produza evidência⌄

Registre identidade, operação, recurso afetado, horário e resultado. Nunca coloque tokens, senhas ou outros segredos no log.

IInformation Disclosure: autorize e minimize⌄

Verifique a autorização sobre o recurso, mesmo para uma pessoa autenticada, e devolva somente os campos necessários para a finalidade.

DDenial of Service: limite o custo⌄

Um limite de requisições reduz a chance de um único usuário consumir recursos suficientes para bloquear os demais.

EElevation of Privilege: exija permissão explícita⌄

Operações administrativas precisam verificar a permissão confiável no servidor e as condições de responsabilidade sobre o recurso.

2. Por que o servidor não deve copiar todo o JSON recebido para a matrícula?

O cliente pode informar a intenção; o servidor define os estados sob sua autoridade.

Ver transcrição de referência ⌄

A aula aplica STRIDE ao sistema de matrículas. Para spoofing, a identidade do estudante deve vir da sessão autenticada, e não de um identificador recebido na requisição. Para tampering, o cliente informa somente sua intenção, enquanto o servidor recupera entidades e calcula prioridade, status e demais regras.

Para repudiation, toda alteração relevante produz uma trilha de auditoria sem segredos. Para information disclosure, o sistema autoriza o acesso ao recurso e minimiza os dados devolvidos. Para denial of service, limita requisições e operações custosas. Para elevation of privilege, exige permissão explícita para operações reservadas.

O encerramento conecta ameaça, requisito, arquitetura, código, teste e evidência. Testes de segurança devem cobrir alteração de identidade, acesso sem permissão, concorrência pela última vaga, repetição de requisição e dados inválidos, sempre verificando o comportamento esperado no servidor.
